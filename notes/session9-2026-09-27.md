# Session 9 (2026-09-27): the Model S MCU2 firmware (2026.8.3)

Goal: find out what the Model S firmware image is and how far it is from running like the
Model 3 one (2019.20.4.2). Work on branch `model-s`. Analysis first; the profile structure is
proposed to the user before anything gets restructured.

## The files
- `firmware/2026.8.3-models/2026.8.3.mcu2` (moved from the repo root, untouched): exactly
  2944 MiB = one of the car's firmware partitions dumped whole. Squashfs 4.0 (lz4 -Xhc, 1.8 GB,
  built 2026-03-13), then a dm-verity table + hash tree, then zeros to the partition's end.
  The Model 3 file has the same squashfs + verity layout, without the padding (moved to
  `firmware/2019.20.4.2-model3/`). `unsquashfs` ignores everything after the squashfs.
- The user also has an older S firmware, 2025.20.6 (Buildroot 2024.11.2, glibc 2.35, same
  architecture as 2026.8.3), extracted, plus BIOS flash dumps and a Tegra NOR dump
  (private; not used). A fallback if 2026.8.3 needs something newer than a PC offers.
- `sandbox/rootfs-s/`: a user-owned copy, extracted without sudo (`unsquashfs -no-xattrs`;
  owners and device nodes are lost, as with `sandbox/rootfs`). The two `*.dirsquashed` files
  (squashfs images the firmware loop-mounts over folders at boot, `bin/mount-all-dirsquashed`:
  `deploy/seed_artifacts_v2` and the web owner's manual) are not unpacked yet.

| | 2019.20.4.2 (Model 3) | 2026.8.3 (Model S) |
|---|---|---|
| base | Tesla's own build | Buildroot 2025.05.1, crosstool-NG |
| glibc | 2.22 | 2.41 (the host's 2.39 is older: host libraries load in the chroot) |

| Qt | 4.8.7 | still 4.8.7 (+ QtWebKit 4.9.4) |

| Mesa | 11/12 era (the kit adds 18.0.5) | 25.0.7, only iris + crocus: **no llvmpipe/softpipe** |
| UI | `Model3CenterDisplay` | `ModelSCenterDisplay`, Model S/X panels/popups; no Model 3 classes: this QtCar is S/X only |
| cluster | none (the Model 3 has one screen) | `QtCarCluster` (runit `qtcar-cluster`), a second process on X screen `:0.1` |

- `/etc/RunQtCar.env`: `UI_PLATFORM=SX`, `QCSIZE=1200x1920` (portrait), `QCTOUCH=evdev:/dev/input/touch,rotate:90,range:4096,invertX`,
  `QCICRES="--window 1.5"`, `QCCRATE=48` (cluster frame rate), `QCIC=100` (the cluster runs on
  the MCU itself: IC address = CID address), gateway ports `QCPORT=:20101`, `QCTXPORT=:20100`
  (Model 3: 1234/4321). 20100 is tesla-can.py's control port today: has to move.
- X: `/etc/X11/xorg.conf.d/10-monitor.conf` has two screens in Zaphod mode: screen 0 "Center"
  on eDP1 (a landscape panel with `Rotate left` = 1200x1920), screen 1 "Cluster" on DP1. QtCar
  gets `DISPLAY=:0.0`, QtCarCluster `DISPLAY=:0.1 ... --isic --ic ...`. The firmware starts its
  own Xorg (runit `x`, intel driver); an optional compton compositor (`--external-compositor`).
- CAN database: `GUICanCracker::crackMessage` is still in libQtCarVAPI, but
  `vehicle/extract-can-db.py` fails reading libQtCarCANData's tables (layout changed; the lib
  is 3x larger). To port.
- `Logger::logAssert`: asserts only log here ("WARN ASSERTION FAILED", QtCar goes on); no
  `utils-assert-nonfatal` patch needed.
- escalator: still there (`/usr/bin/escalator`, runit `escalator`), references compton and
  chromium-app; QtCar ran without it so far (it's CEF that needed it in 2019).
- QtCar's libraries all resolve inside the rootfs (plus `usr/lib/engines-3` for libtpm2tss).

## What this means
- Much closer than the Model 3 was in session 1: no binary patches so far, only software GL.
  The kit's Mesa for this profile: Debian 13's Mesa 25.0.7 (same version as the firmware, built
  against glibc 2.41) or the host's; to decide.
- The screen: Xvfb with two screens (`-screen 0 1200x1920x24 -screen 1 1920x720x24`) would
  reproduce the car's `:0.0`/`:0.1` exactly; VNC one port per screen. `--native` later.
- Vehicle data is the big job: no simulator, so tesla-can.py has to produce the S's gateway
  traffic (port 20101) itself, from an S CAN database (the extractor needs porting). The
  Model S uses other buses/IDs than the Model 3.
- Browser: Chromium 140 as a service with its own sandbox (chrome-sandbox, cgroups); the 2019
  CEF work doesn't apply.

## The kit profiles (agreed with the user)
One repo, one main branch; per firmware version a kit profile, per car type the vehicle parts.
- `mcu2-patchkit/mcu2_patch.py` is the engine; `profiles/2019.20.4.2-model3/` has the Model 3's
  tables (moved unchanged into `kit.py`), its `sources.toml` and shims (`src/`);
  `profiles/2026.8.3-models/` the S's. `profile.toml`: `[detect]` version + UI_PLATFORM + car,
  `[screen]` center/cluster sizes, `[features]` maps. Detection from customerVersion.txt and
  RunQtCar.env; `--profile`, `--profiles`, `--detect`, `--info` (key=value for the shell tools).
- Payload cache per profile (`payload/<profile>/`; the old `payload/<path>` is taken over when
  the hash matches). Kit version: engine + shared src/ + the profile folder (not sources.toml);
  the stamp gets `profile=` (none = Model 3). The Model 3's hash changed with the move:
  `./tesla check` asks for one `./tesla build-image` (only the stamp changes).
- Regression: `--check` of the old kit (worktree of the previous commit) and the new one on
  `sandbox/rootfs`: identical item by item; the Model 3 sandbox still runs.
- S profile: Debian 13's Mesa 25.0.7-2+deb13u1 (+ glvnd 1.7.0, LLVM 19, libdrm 2.4.124, and
  libbsd, libedit, libmd, libsensors5, libtinfo6, libwayland-client/server, libz3, libzstd,
  which the firmware lacks: checked with its loader) in `/opt/mesa`, `env.sh` to source.
  QtCar + QtCarCluster on one Xvfb with two screens (`:98.0` 1200x1920, `:98.1` 1920x720) with
  it: both run, no crash, no restart.
- `./tesla`: `--config FILE` works with every command and anywhere on the line (taken out of the
  arguments before the command sees it); settings `DUMP` (default ./mcu2-original) and
  `SANDBOX_ROOT` (default ./sandbox/rootfs) for build-image; `tesla-s.conf` (untracked) has
  `IMAGE=./mcu2s.ext4`, `DUMP=./mcu2s-original`, `SANDBOX_ROOT=./sandbox/rootfs-s`. The maps
  step is skipped for profiles without `maps = true`.

## The real chroot and --native on the T480 (user: chroot/native before the other services)
The laptop's live system (Debian 13, sudo) had been rebooted: xvfb, x11vnc, xdotool,
imagemagick, tmux installed again; the repo files (as build-stick picks them), tesla-touch and the
kit's S payload copied to ~/mcu2-desktop; the squashfs part of the partition (1.9 GB, 17 s over
the LAN) unpacked there as root into a temporary dump (DUMP=/home/user/mcu2s-original in the
laptop's tesla-s.conf), then `./tesla --config tesla-s.conf build-image --fresh --no-maps`.
Everything in the live system's 12 GB RAM overlay (the NVMe has another system: not touched).
- `./tesla start` with the profile: SIZE from `[screen] center`, a second Xvfb screen for the
  cluster (`:1.1`, x11vnc on VNC_PORT+1), QtCarCluster in its own restart loop (cluster.log);
  natively no cluster yet (one screen). run_startup passes QTCAR_BIN/QTCAR_SIZE; the S kit's
  /startup.sh runs QtCar or QtCarCluster with chpst (the users' shell is /bin/false), the kit's
  Mesa in software, the firmware's own Mesa on an Intel GPU.
- Black screens in the chroot, "MESA: error: Failed to attach to x11 shm" x 2886: QtCar (uid
  1111) creates the segments 0600, Xvfb (the laptop's user) can't attach them, and Mesa's
  swrastPutImageShm then drops the frame (no fallback). The sandbox ran everything as one uid.
  The car's X has MIT-SHM disabled (20-extensions.conf): `mit_shm = false` in profile.toml,
  Xvfb `-extension MIT-SHM`; Mesa uses plain PutImage then.
- QtCar restarts itself on the first starts ("Restarting QtCar because of changed DVs": exit
  137 like a Ctrl+C); start.sh knew only "CID UI is restarting" and took it as a stop. Now both.
- Touch: "Evdev: /dev/input/touch not open" every second, no open() at all. The touch driver
  opens only while the display is on: CD_displayState 1..9 (and POWER_touchState). The display
  state machine (DisplayStateOff, handlers for doors, driver present, brake, power requests)
  never leaves Off without vehicle data and ignores touches ("ignoring touch N secs after last
  display off"). `[display_state] enable_display_state_manager=false` in settings.conf (kit):
  the display counts as on, the driver opens the device, taps work (app launcher opened).
- Data values: the HTTP `_data_get_value_request_` answers `{  }` in this firmware. The system
  D-Bus is the way now: QtCar registers com.tesla.CenterDisplay (+ ClusterDisplay, CarAssist*)
  with /LocalDataValue, interface com.tesla.LocalDataValue: DataGetValueRequest(s) -> (b, s),
  DataSetValueRequest(s, v) -> b. The firmware's lv/sdv use com.tesla.Debug (another service).
  The S startup.sh starts the system dbus-daemon once (warnings about the car's missing users
  are harmless). In the chroot:
  `dbus-send --system --print-reply=literal --dest=com.tesla.CenterDisplay /LocalDataValue com.tesla.LocalDataValue.DataGetValueRequest string:VAPI_carType`
  -> ModelS.
- --native (Xorg on the laptop, eDP-1 1920x1080): QtCar segfaulted in QEgl::chooseConfig (no
  configs). eglinfo in the chroot: "MESA-LOADER: failed to retrieve device information", "using
  driver i915", "i915: driver missing". libdrm finds the PCI id through /sys/dev/char/226:N; the
  chroot had only /sys/class and /sys/devices. start.sh binds /sys/dev too: "pci id 8086:5917,
  driver iris", Mesa Intel UHD 620 (KBL GT2). QtCar ~10% CPU on the GPU.
- tesla-touch in touchscreen mode got no --size (default 1920x1200, the Model 3's): now SIZE.
  The ELAN touchscreen is passed through as a 1200x1920 device, the UI pillarboxed on the panel.
  Not tried with a finger yet (needs the user).

## Services and vehicle data (first steps)
- The S kit installs the shared qtcar-service and sv wrapper. qtcar-vehicle runs as is
  (`--udp :20101 --udphp :31415 --udptx :20100`).
- Services meet in /tmp/dvaccess (Unix sockets, group dvaccess, 770): the S startup.sh does what
  the car's qtcar-startup job does, and QtCar/QtCarCluster get their supplementary groups
  (chpst -u user:group:... from the chroot's /etc/group; minijail gives them on the car).
  qtcar-service does the same for minijail jobs without QCGROUPS (also the Model 3's
  gpsmanager, audiod, mediaserver, bluetooth: not re-tested on the Model 3 image yet).
- The system D-Bus as a profile base service (`[services] base = ["dbus"]`): started first,
  ./tesla waits for its socket (qtcar-vehicle started before QtCar's own dbus-daemon and never
  registered com.tesla.VehicleService).
- `[PEERSEC] Failed to get peersec ... Protocol not available`: the data value listeners check
  the publisher's AppArmor label (SO_PEERSEC) and dropped every connection; QtCar never got
  QtCarVehicle's values. `[service_data_listener] sec_prof_check=false` (kit, settings.conf).
- CAN database: extract-can-db.py reads every `<BUS>_messages` table (the S: BDY 1, BFT 3, CH 5,
  ETH 6, PT 2, TH 4: bus numbers found by trying each cracker), emulates libQtCarDiag's
  Diag<BUS>Cracker (or GUICanCracker) and understands in-place pointers (DT_RELR). 1728 messages,
  41401 signals, 39779 with a layout; the gateway's copies on other buses are "<name>@<BUS>".
  The Model 3's output is byte-identical. -> vehicle/work/can-db-models.json (per car type).
- QtCarVehicle on the S reads only the gateway's ETH stream: UdpVehicleLink::processReadyETHSocket,
  datagram = 32-bit big-endian id + data (the Model 3: 16-bit), handlers looked up by id.
  tesla-can.py: HEADER/TX_PORT from the database (S: 4 bytes, requests on 20100), only ETH
  messages, signals without layout dropped; control port 20100 -> 20180 (also tesla-gps.py);
  `--all-zero` sends every ECU message (not UI_*/MCU_*) with zeros (for exploring).
- Findings so far (disassembly of libQtCarVAPI with the GOT slots resolved to their symbols:
  objdump's `<sym@@Base-0x...>` comments name the nearest symbol, not the target):
  - VAPI_driveRailOn = GTW_gatewayStatus (0x031) byte 4 bit 1 = GTW_vehiclePowerState in the DB
    (not GTW_driveRailRequest); byte 0 bits 2/4 = hvac/acc rail (ModelS_GatewayStatusMessage).
  - gear: DI_torque2 (0x004) DI_gear: P works (VAPI_shiftState P in QtCar).
  - battery/range: EnergyStatusMessage (BMS_energyStatus 0x386) scales with
    VehicleUtils::fullPackEnergy = BMS_nominalFullPackEnergyRemaining x softPackLimitPct
    (VAPI_soePctLimit, GUI_energyLimitPercent); the pack from VAPI_packConfig/softPackConfig
    (car config) via ModelSVehicleLink::packConfigChanged. Still 0 %.
  - with the zeros: climate shows 21.0, seat heaters appear; the cluster still "Car Off".

- Battery/range: the S takes its whole car configuration from the gateway's GTW_carConfig*
  messages (pack, drive units, performance, chassis, wheels, country). GTW_packConfig indexes
  libQtCarVAPI's packTypeParams (56-byte entries): 24 = 85 kWh, 265 mi rated, 257.5 Wh/mi (1-14
  are placeholders). GTW_packConfig=24 GTW_softPackConfig=0 (other soft values: "mismatch") ->
  VAPI_packEnergy Energy85, battery 69 % with BMS_nominalEnergyRemaining=60, 196 mi.
- tesla-can.py's control reply held all 14000 --all-zero values ("Message too long"): a set gets
  back only what it set, the status is cut to fit.
- The cluster read its own settings.conf (/home/qtcluster): 2688 PEERSEC errors, the publisher
  sockets churned. startup.sh links the shared one there (like qtcar-service for services).
- Shared memory data values (DVSM_*: drive rail, car state, ... for QtCar and the cluster):
  every publisher and listener passes create=false to SharedMemoryBuffer; QtCarStartup (the car's
  qtcar-startup job, root with groups :root:dvshm) creates them all at boot ("Created shared
  memory DVSM_... with N entries", "signaling startup complete"). They're SysV semaphores and
  segments with mode 660 in the creator's primary group: dvshm first as primary group for its
  members (startup.sh, qtcar-service), stale objects of the chroot's users removed at every start
  (they outlive the run in the host's IPC namespace; one from an earlier run blocked everything).
  Base services now: dbus qtcar-startup qtcar-dvserver (QtCarDvServer: data values for other
  services). Result: VAPI_driveRailOn true in QtCar; the cluster shows the speedometer (0 mph),
  the car, P R N D, 69 %.

- `./tesla --config tesla-s.conf start --vehicle`: the CAN database per car type
  (`can_db`: vehicle/work/can-db.json for the Model 3, can-db-<car>.json otherwise, extracted at
  the first start), no qtcar-sim for the S, tesla-can.py with `--db ... --all-zero --preset
  parked` (PRESETS_SX, chosen by the database; default target :20101 for the S format). The stick
  takes the image's database. Tested on the T480: all of the above comes up by itself.

- GPS: qtcar-gpsmanager runs as is (NMEA on :63277): LOC_geoLat/Lon follow tesla-gps.py, valid
  fix. tesla-gps.py --can speaks the Model 3's signals: for the S tesla-can.py skips SIM_* and
  unknown ones from it and converts DI_vehicleSpeed (the S's DI_torque2 is in mph).
- Map tiles: none requested (TileManager n_downloads=0), also with qtcar-checkinternet; the
  tile cache dir was root-owned (startup.sh/qtcar-startup now chown tesla's .Tesla dirs). Google
  semantic/vector tiles probably need Tesla-side authorization and the car's connectivity state:
  open.
- --native: the cluster on its own Xvfb (:1) with VNC on VNC_PORT+1, in software GL.
- QtCar's panel control: CenterDisplayDevice/DriverDisplayDevice switch the car's outputs (eDP1,
  DP1) with xrandr about once a second, because their powered/link checks go through the
  escalator (drm-status-detect, read-dpcd, CLUSTER_POWER), which isn't running. Natively each
  xrandr call probed the real outputs: frame stalls up to 1.2 s ("BadFrameStats"), and with the
  intel X driver on a PC (outputs also named eDP1/DP1) it would switch the PC's screen. The S kit
  wraps xrandr (output changes ignored, queries passed on; the firmware's is xrandr.real, engine:
  KEEP_BINARY): no stalls, but the loop now runs ~30x/s, QtCar ~60 % CPU on the T480.
  Not running the real escalator unattended: it can reboot the machine, format USB drives,
  write GPIOs (and without Tesla's AppArmor hats it refuses all commands anyway: aa_change_hat
  EPERM in the sandbox). Its protocol (for a stub later): client -> 0xff, u32 command length,
  u32 input length, "[detached ]<command> <args>", input; reply u32 exit code, u32 output length,
  output. drm-status-detect: only the exit code counts; DisplayPortDevice::isTrained wants
  >= 0x11f DPCD bytes from read-dpcd; DriverDisplayDevice::isPowered first checks
  VAPI_busSleepState, then read-dpcd.
