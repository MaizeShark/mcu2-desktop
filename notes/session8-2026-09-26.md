# Session 8 (2026-09-26): the bootable USB stick

The user's pick for this session: a script that builds a bootable live image from the user's own
image, starting straight into `./tesla start --native`. Result: `./tesla build-stick` + `stick/`
(details in `stick/README.md`).

## Decisions (with the user)
- Debian 13 (as on the T480 test laptop), its stock 250 Hz kernel: the audio clock (snd-dummy
  hrclock as snd-aloop's timer, session 6) already handles it. A 1000 Hz kernel (Ubuntu 24.10+
  or a rebuilt Debian one) would only make that workaround unnecessary; it doesn't help the
  dropouts in games (realtime audio threads, heat).
- Persistence: yes. Secure Boot, ssh, keyboard/time zone: options (`--secure-boot`, `--ssh`,
  `--keymap`/`--timezone`, defaults from the build host: de, Europe/Berlin here). The started
  features: from the build's tesla.conf, camera and Bluetooth `auto`. Keys instead of a desktop.
- UEFI only for now.

## How it's built (no sudo on the PC)
- mmdebstrap works in rootless podman (`--privileged`, `--mode=root`): the whole build runs in a
  container `localhost/mcu2-stick-builder` (Debian 13 + mmdebstrap, squashfs-tools, mtools,
  GRUB, shim-signed). The rootfs lives only in the container; the base system is cached as a
  tar per package list (`stick/work/cache/base-<hash>.tar`, debs in `cache/debs`). First build
  ~5 min, later ones ~3 min.
- Extracting that tar in the container can't mknod (`./dev/console: Cannot mknod`): /dev is
  skipped, the squashfs gets console/null/tty as mksquashfs pseudo files.
- Disk: GPT, partition 1 FAT32 `TESLABOOT` (GRUB, kernel, initrd, squashfs 678 MB), partition 2
  ext4 `persistence` (live-boot `persistence.conf`: `/home`, `/var/lib/bluetooth`,
  NetworkManager's connections). `mke2fs -d` fills it; the 6 GB image is bind-mounted into the
  staging folder instead of copied and its owner set with debugfs afterwards. 8.6 GB image,
  5 GB used. GRUB: `grub-mkstandalone` with an embedded config that finds the partition by its
  label; `--secure-boot`: shim (EFI/BOOT/BOOTX64.EFI) -> Debian's signed grubx64.efi, which
  reads EFI/debian/grub.cfg (the same finder).
- The stick gets the files git tracks or would track (`ls-files --cached --others
  --exclude-standard`; an uncommitted new tool was missing at first), tesla-touch's binary and
  the CAN database.

## On the stick
- getty autologin on tty1 (user mcu, uid 1000, sudo without password) -> /etc/profile.d ->
  `tesla-start` (startx) -> `tesla-session`: xbindkeys, then `./tesla start --native` in a loop.
  No window manager: QtCar fills the 1920x1200 framebuffer by itself, game-windows.py already
  handles "no WM" (VNC mode). Rootless Xorg through logind works from the autologin session.
- `tesla-key`: Ctrl+Alt+Esc (flag file with the reason + `./tesla stop` -> X ends -> console with
  `tesla-help`), Ctrl+Alt+Backspace (`./tesla stop`, the loop starts it again), Ctrl+Alt+End
  (power off). 3 failed starts within 60 s each -> console.
- `tesla-grow.service`: growpart + resize2fs of partition 2 at the first boot (the image is only
  as large as its contents + `--free`).

## Tested in qemu (`stick/qemu.sh`: OVMF, KVM, the image as usb-storage through a qcow2 overlay)
- Boots, live-boot mounts the persistence partition, grows it to the 16 GB virtual stick, X
  starts, `./tesla start --native` runs everything (software rendering, virtio-gpu; the audio
  clock came up on the 250 Hz kernel; the letterbox on 1920x1080). Screenshot: the car, map,
  vehicle data.
- The three keys work. `sudo reboot` while running: a marker in ~ and a tesla.conf change
  survive, a file in /etc doesn't, the image needed no journal recovery (systemd unmounts it);
  only events.log lacks its "stop" line (everything gets SIGTERM at once).
- `--secure-boot` with OVMF secboot + Microsoft keys: "Secure boot enabled", lockdown, QtCar
  runs; v4l2loopback "Key was rejected by service" (dkms module unsigned) -> no camera. Signing
  it with a MOK (enrolled once through MokManager) would fix that; not done.

## Fixed on the way (also for PCs)
- **Console flood**: after Ctrl+Alt+Esc tty1 was full of `QtCarGpsManager[1769]: ... INFO ...`.
  The image's /dev/log -> ../tmp/log has no listener, so glibc's syslog (LOG_CONS) wrote to
  /dev/console. On a PC that's the hidden text console. Now `tools/syslog-sink.py` listens at
  the chroot's /tmp/log and writes `logs/<run>/syslog.log` (~2000 lines at the start, then ~5/s,
  mostly the simulator's LOC_estimatedGeoTimestamp pushes: ~2 MB/h). The services' own log lines
  were never visible before: useful for debugging.
- **CAMERA=auto / BLUETOOTH=auto** in ./tesla itself (start, check, config): `find_camera` =
  the capture node (index 0) of a UVC device whose name doesn't say IR. The T480's IR camera
  offers MJPG/YUYV too, so the v4l2-ctl format test picked it; sysfs + name it is.
- **Loop device check by inode** (`loop_devs_of`): on the stick /home is a bind mount, the loop
  device records /run/live/persistence/sda2/home/..., and `losetup -j` compares paths unless it
  may open /dev/loopN (a user may not; on Debian losetup isn't even in a user's PATH): false
  "chroot has /dev/loop1 mounted, not mcu2.ext4". Now sysfs backing_file + stat.

## The T480 from the stick (evening)
- Black screen on two cheap sticks: both USB 2 (the "USB 3" one is an Alcor 058f:6387, 480 Mbit/s),
  12 MB/s sequential read, and the services' small synchronous writes (settings DBs, journal)
  stalled them at 17 KB/s with 97% I/O pressure; QtCar sat in D state, no log line in 6.5 min.
  From a RAM copy of the image QtCar was ready in seconds.
- **IMAGE_RAM** (start.sh/common.sh): on a USB drive the chroot runs on a dm snapshot with its COW
  store in /dev/shm; the teardown applies it with tools/cow-apply.py (parses the persistent COW
  format, one fsync). dm's snapshot-merge flushed per 4 KiB chunk: 4.5 min for 3.7 MB. Verified
  against real dm snapshots (185 chunks and 3879 chunks over 16 metadata areas: checksums match).
  QtCar ready in 13 s (39 s cold) from the 12 MB/s stick. dmsetup added to the stick.
- One image on a stick had a corrupted directory (a perl dir nobody writes, one block all 0x60).
  f3probe: the stick has its real capacity; cow-apply verified. Most likely the hard resets
  during the stalled writes (cheap flash). Stick advice: USB 3 with a stated write speed, or a
  USB SSD.
- The Model S idea: VAPI_carType 0 = ModelS, 1 ModelX, 2 ModelS2, 3 Model3, 4 Truck. The simulator
  only supports 3 (SimUtils::isCarTypeSupported table 00 00 00 01 00), QtCarVehicle forces
  Model3, and even with all forced (sandbox, patched table) the UI is Model3CenterDisplay with
  Model 3 views; ModelS/XHeroView classes exist but aren't used. das-viz/ego/S and X (driving
  visualization models) are complete: untested whether the D view uses them.
- `--resolution WxH` (branch `resolution`, VNC only): QtCar's --size is a window size, its layout
  stays 1920 wide at 1:1.

## Wi-Fi (--wifi)
- The firmware's stack: wpa_supplicant 2.6 (-u, D-Bus), connmand (-n -I eth0,eth0.2 on the car),
  QtCarConnMan (qtcar-connman, root). QtCarConnMan needs an interface named wlan0
  (QNetworkInterface, "invalid wifi interface") and powers Wi-Fi through connman's technology;
  service-wifi only adds Tesla's service network profile; wifi-power is the car's GPIO/PCI switch
  (stubbed by the kit).
- start.sh: NetworkManager unmanages the adapter, rename to wlan0, services dbus wpa_supplicant
  connman qtcar-connman; restore_wifi renames back and gives it to NM. connmand -r -i wlan0.
- The user ran it on the PC (I must not: network takeovers on the PC are off limits): joined their
  WPA2 network through QtCar's settings, LINK_wifiState online, restored cleanly. Stick: WIFI=auto.
