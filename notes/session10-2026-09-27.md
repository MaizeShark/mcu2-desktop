### Force NativeMaps Internet Connectivity

`NativeMaps::TileManager::manageConnectivity()` determines internet availability using both the display state and `GUI_canUseInternet`:

```asm
movzx  r14d, BYTE PTR [rbx+0x4b]  ; GUI_canUseInternet
test   r15d, r15d                  ; display state
setg   al
and    eax, r14d                   ; internet = displayOn && canUseInternet
```

Runtime testing with GDB confirmed that changing `GUI_canUseInternet+0x4b` from `0` to `1` caused `manageConnectivity()` to report `internet: true` and allowed the required data to download.

To make this permanent, the read of `GUI_canUseInternet` is replaced with an instruction that forces the low bit of `r14d` to `1`:

```text
Offset:   0x272b1e8
Original: 44 0f b6 73 4b    movzx r14d, BYTE PTR [rbx+0x4b]
Patched:  41 83 ce 01 90    or r14d, 1; nop
```

This forces the `GUI_canUseInternet` side of the condition to true while preserving the existing display-state check. As a result, NativeMaps considers internet available whenever the display is on.

## Follow-up: T480 tile requests (2026-09-28)

The T480's image has the exact patched bytes, and its QtCar log says `manageConnectivity
internet: true display on true`. It sends vector tile requests. The first failed request
returned HTTP 400 with `region_code is required when include_disputed_entity_context is false`:
its URL had an empty `region_code`. The PC's persisted `map/MapCountry` is `US`; the T480's was
empty, with `VAPI_countryCode` and `VAPI_priorCountryCode` both 0. Thus the binary patch did
work on the T480; a second required input was missing.

The T480's `QtCarSettings.db` was backed up locally
and seeded with `VAPI_countryCode=21843`, `VAPI_priorCountryCode=21843` and
`map/MapCountry=US` while QtCar was stopped. The Model S `parked` CAN preset now sends
`GTW_country=0x5553` (ASCII `US`) and `GTW_mapRegion=us`; its offline frame encoding was
checked. Live tile rendering was verified on the T480 in both VNC and `--native` mode: the map
showed roads/labels, and the native run's tile logger counted 134 successful `TileNetworkLoad`
events with no bad tile requests. The patch only bypasses TileManager's connectivity gate; it
does not set the country or make other online features work.

The live run also exposed an unrelated stale SysV IPC issue: `qtcar-startup` could not create
some `DVSM_*` segments because root-owned objects from older runs remained, and `qtcar-vehicle`
segfaulted repeatedly with mismatched shared-buffer sizes. `tools/start.sh`'s `clean_ipc` had
compared numeric chroot UIDs to the names printed by `ipcs` and missed root-owned objects in the
chroot's `dvshm` group. It now reads numeric `/proc/sysvipc` fields and clears unattached
segments / semaphores owned by chroot users or the `dvshm` group. On the next T480 run,
`qtcar-startup` reported no existing segment errors, `qtcar-vehicle` stayed up, and the tile
logger counted another four successful network loads. The run was stopped; Xfce returned to
1920x1080. The image was already mounted at `chroot/` and remains so.

## Follow-up: host connectivity data values (2026-09-28)

The map patch let only TileManager ignore `GUI_canUseInternet`; media still logged `internet:
false`. In `CenterDisplay::checkInternet()` the firmware sets `GUI_canUseInternet` from a usable
route (`WifiManager::usingWifi()` or `OptionsManager::dataPlanOn()`),
`CONN_connectedToInternet`, and `!ForceNoInternet`. `usingWifi()` checks whether
`LINK_linkState` contains `wifi` (case insensitive). Without QtCarConnMan the normal
`/tmp/dvaccess/Connectivity.sock` publisher is absent, so `CONN_connectedToInternet` is invalid.

In the unpatched Model S sandbox, D-Bus `DataSetValueRequest` for `LINK_linkState=Wifi` and
`CONN_connectedToInternet=true` made `GUI_canUseInternet` true and TileManager log `internet:
true`; setting `CONN_connectedToInternet=false` reversed both. With `OPTION_dataPlan=0`,
`CONN_connectedToInternet=true` alone left the GUI offline, then `LINK_linkState=Wifi` made it
online; switching `CONN_connectedToInternet` back to false took it offline again. The host bridge
was also exercised end to end against that sandbox through its actual `publish()` function.
`tools/host-connectivity.py`
probes a keyless HTTP 204 endpoint from the host and updates those source data values every 15 s
(also after QtCar restarts). The profile now retires the TileManager patch and restores its
original bytes when the kit updates an existing image. The PC and T480 images were updated and
tested with the original TileManager bytes; maps loaded tiles on both.

The first T480 media test still logged `internet: false` with `GUI_canUseInternet=true`.
`MediaSystemStateControllerImpl::updateInternetAvailable()` in `libQtCarMediaV2` reads
`LINK_wifiState` and `LINK_cellState`, independently of the GUI flag. On the live T480, setting
`LINK_wifiState=online` through `DataSetValueRequest` made Apple and Amazon Music log connectivity
restored and Apple Music's `readyToWakeBrowse()` log `internet: true`. Setting it to `offline`
made both log connectivity lost and Apple Music `internet: false`; restoring `online` restored
both. The bridge now publishes `LINK_wifiState` too. Browser and streaming login requirements
remain separate from this connectivity signal.
