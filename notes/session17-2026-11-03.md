# Session 17 (2026-11-03): a MITM CA for the car (`--mitm-cert`)

Goal: let the user watch the Model 3's HTTPS traffic with an intercepting proxy (mitmproxy).

## The firmware's TLS stores (Model 3, 2019.20.4.2)
- OpenSSL 1.0 (`OPENSSLDIR /etc/ssl`): `/etc/ssl/certs` with hashed links (`<hash>.0`, the
  1.0 subject hash = OpenSSL 3's `-subject_hash`) and `ca-certificates.crt` (133 certs);
  no `/etc/ssl/cert.pem`, no update-ca-certificates or c_rehash.
- libcurl: `/etc/ssl/certs`. QtCar is Qt 4.8.7 (`libQtNetwork.so.4`): its list of CA dirs
  starts with `/etc/ssl/certs/`.
- CEF 3.3683 (Chrome 73) links libnss3 (NSS 3.39) and verifies through it
  (`cert_verify_proc_nss`). The real image has `/home/tesla/.pki/nssdb` (uid 1111: QtCar runs
  CEF in-process as `tesla`); the sandbox's is `/root/.pki/nssdb`.
- Pinned: `/etc/tesla_motors-ca.crt`, `/etc/hermes-eng-ca/` (Tesla's backend).

## Implementation (`tools/start.sh` `mitm_stage`, `start_mitm_cert`)
Per run, nothing in the image: a copy of `/etc/ssl/certs` plus the CA in `logs/<run>/mitm/certs`,
bound read-only over the original; a tmpfs over `$HOME/.pki/nssdb` of `tesla` (and the S's
`chromium*` users) with a fresh DB from the host's certutil, trust `C,,`. Checks in check.sh.

## Pitfall: PKCS#11 3.2 trust objects
The first browser test failed with `CERT_PKIXVerifyCert for localhost failed err=-8172`
(SEC_ERROR_UNTRUSTED_ISSUER; a self-signed site gives -8179, unknown issuer): NSS found the CA
but no trust. Fedora's certutil (NSS 3.131) wrote the trust as `CKO_TRUST` (class 0x0B in
`nssPublic.a0`); NSS 3.39 only knows `CKO_NSS_TRUST` (0xCE534353). `NSS_TRUST_TYPE=NSS`
(an env var in the host's libnss3) makes certutil write the old one.

## Pinned Tesla anchors
Tesla's own clients (QtCarServer, QtCarConnMan, QtCarTMServer; hermes_proxy is absent, /opt/hermes
empty) don't use /etc/ssl/certs for the backend. RunHermes.vars launches hermes_proxy with
`--ca=/etc/ca.crt --cert=/var/lib/car_creds/car.crt --key=.../car.key` (mTLS); the apparmor
profiles grant those four processes read on /etc/ca.crt, /etc/tesla_motors-ca.crt and
/etc/hermes-eng-ca/{products,root}-ca.crt. QtCarServer links libcurl + libQtNetwork and talks to
mothership.vn.teslamotors.com (loopback in /etc/hosts), logupload-*/telemetry-*.vn.tesla.services.
start_mitm_cert now also appends the CA to each pinned file that exists (bind-mounted copy =
original + CA, additive so the real pins still verify). Checked with openssl verify: the test leaf
chains to /etc/ca.crt + CA, originals still parse. Not exercised against the real clients: they
need the car credentials (/var/lib/car_creds), which the dump doesn't have, so endpoints that
require the client cert fail the handshake before the request; the rest are visible to a local
stub. The backend hosts point at loopback or real Tesla DNS, so there is no live upstream to relay.

## Tests
- Test CA + leaf for localhost (openssl), `openssl s_server -WWW` on 127.0.0.1:8444.
- Firmware curl / `openssl s_client -CApath /etc/ssl/certs` in podman: 000 / verify error 21
  without, 200 / verify 0 with the staged certs dir.
- `CEF_REMOTE_DEBUGGING_PORT=9222 ./sandbox.sh --browser` with the staged DB in
  `sandbox/rootfs/root/.pki/nssdb` (original restored afterwards), driven over DevTools:
  the test page loads ("200 secure", title shown), self-signed.badssl.com still refused,
  example.com fine.
- Not tested: the sudo path of `./tesla start` (mounts), a real mitmproxy session, Qt 4.8 on its
  own, the Model S/X, the stick (libnss3-tools added to its packages).
