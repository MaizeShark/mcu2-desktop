## Chromium segfaults at stop
The teardown sent SIGTERM to every process in the chroot at once. In podman: SIGTERM to the
browser process alone (`tesla-chromium-main` without `--type=`) exits 0; killing its session
D-Bus first gives `FATAL dbus/bus.cc: D-Bus connection was disconnected` (trap). `stop_chroot_procs`
now stops the browsers first (up to 3 s), then the rest: exit 0 in the same test.

## The panel loop: `--emulated`
`DisplayPortDevice::isTrained` first checks `RuntimeEnv::instance()+0x12` and returns true when
set. `RuntimeEnv::setFromArgs` takes `--key value` arguments into a hash; `--dev` sets mode
(field 0, default 2 = prod) to 0 and field 8, `--emulated` also sets 0x12. Field 8 is "development
car" (`/var/run/is-development` exists, many readers: places DB logging, map status, games).
0x12 is read only by CenterDisplayDevice::isPowered/setPower/backlight*, DisplayPortDevice::
isTrained/setOutputEnabled, DriverDisplayDevice::setOutputEnabled and Logger::logAssert, which
skips the crash when prod or emulated (so asserts still only log; with mode 0 they're logged
more: ~38 in 90 s). `read-dpcd`'s answer, for the record: a text dump; isTrained wants more than
0x11f characters and the lane status digits at 0xa8/0xa9/0xab/0xac (minus '0') to have bits 0-2
set (7).

Sandbox with qtcar-vehicle + tesla-can.py `--preset parked` (the loop needs vehicle data; QtCar
alone in the sandbox doesn't run it): 10 204 ERROR lines in 90 s (4126 gpio, 3096 read-dpcd, ...)
-> 350 with `--emulated`; QtCar 148 -> 108 % CPU (llvmpipe); both screens look the same. The S
profile's startup.sh and sandbox.sh pass `--emulated`.

## Escalator stub
Protocol from `libescalator` (escalator-ctl's client; QtCar's QEscalator speaks the same): connect
`/tmp/escalator`, send 0xff, u32 command length, u32 input length (host order), command
(`detached ` prefix: no reply), input; reply u32 exit code, u32 output length, output.
`src/escalator-stub.c` in the S profile (kit-built, base service `escalator-stub` via
qtcar-service, root in the chroot, socket 0666) answers from a table and logs every request to
`escalator-stub.log`; unknown ones are refused (exit 1). What QtCar asks right after a start:
cluster-power 0 (105x in 75 s), pwm-duty-cycle N (backlight, 44x), start-tesla-chromium-app,
start-valhalla, download-tesla-release-notes/-owners-manual, restart-qtcar-speechrecognizer,
restart-car-assist, start-apviz/thaw-apviz, ssh-disconnect-users, enable-xhci-usb-panic, ...
"ok" without action: drm-status-detect, read-dpcd (trained), CLUSTER_POWER/cluster-power,
pwm-duty-cycle(-gen3), start-tesla-chromium-app, start-valhalla. Through `/sbin/sv`:
start-/stop- fireplace, dog-mode, camp-mode, camp-mode-holiday, mame. Theater stays with
theater-control.py (QtCar logs "Starting app via Escalator: ..." before asking).
