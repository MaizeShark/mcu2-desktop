# Session 11 (2026-09-28): Model S/X streaming web stack

Firmware 2026.8.3, Model S/X profile, tested in the real chroot on the ThinkPad T480.
This continues sessions 9 and 10. The image was already mounted at `chroot/`; each test
stopped without unmounting it.

## Browser startup

The profile now starts `media-webapp-server`, the Chromium session D-Bus daemon,
`chromium-adapter`, `chromium-app-input`, and `chromium-app` as base services. Their
`tesla-media-service` wrapper follows the firmware runit scripts without minijail or cgroup v1.
The web server binds only to `127.0.0.1:9000`, the adapter listens on 9001, and Chromium
DevTools binds only to `127.0.0.1:9223`. The web server returned HTTP 200 for the packaged
apps; D-Bus names `com.tesla.ChromiumApp` and `com.tesla.ChromiumAdapterDbus` appeared,
the web app websocket connected, and `./tesla status` reported the jobs up.

The firmware's 14 KiB `chrome_crashpad_handler` exits without the handshake expected by
Chromium 140. A matching Debian Chromium 140 handler is a patch kit payload. The T480 CPU
lacks SHA-NI; the firmware Chromium calls SHA-NI routines unconditionally. Two checked binary
patches redirect the SHA-1 and SHA-256 entries to scalar routines already in the same
executable. The four process executable paths are hardlinks; the kit applies those tiny patches
in place to retain one inode (an atomic replacement would require four 235 MiB copies).

Chromium's offscreen window was mapped and D-Bus connected, but QtCar's media area remained
black: Xvfb/llvmpipe cannot import its X pixmap as an EGL image. The profile's
`egl_media_pixmap_shim.so` copies the pixmap into the texture when import fails. This rendered
TuneIn artwork and cards in QtCar. The earlier Model 3 shim's unrelated CEF hooks are omitted.

## VNC touch

The firmware `input-to-virtual` config assumes a 4096-unit rotated physical sensor. The
`tesla-touch` virtual sensor reports 1200×1920 screen pixels. For a VNC click at (160,1500),
the original input config transformed it outside Chromium's browse rectangle. Removing
`range=4096`, rotation and X inversion made the helper emit browser coordinates (150,520).
Xvfb does not attach that uinput device as an XInput device, however. `tools/media-touch.py`
reads the same virtual touch source, uses the geometry file QtCar writes, and sends touch events
to Chromium through its localhost-only DevTools socket. A VNC tap on TuneIn's Music card opened
the station category, and a tap on a station started playback. Native mode retains the firmware
input helper; its touchscreen path was not proven in this session. An earlier native T480 run
restored the rotated eDP-1 panel to normal on stop, but did not map the ChromiumApp window.

## Connectivity and source results

`host-connectivity.py` now publishes `CONN_wifiConnected` as well as `LINK_linkState=wifi`,
`LINK_wifiState=online` and `CONN_connectedToInternet=true` to CenterDisplay and DvServer.
ChromiumAdapter sent `WifiConnectedChanged true`; the false Premium Connectivity gate cleared.
SpotifyServer logged `setConnectivity: Wireless`, QtCar reported
`SPOTIFY_sdkHasConnectivity=true`, but Spotify remained `LoggedOut`/`NeedAcceptTC` and QtCar
said `no credentials saved`. `GUI_currentProfileUUID` was empty.

In the later native T480 run, the user completed YouTube Music's external Google activation
twice. The page still showed login. Chromium logged `Failed to fetch` when polling
`/vehicles/youtube_music/auth_token` at `mothership.vn.teslamotors.com:9002`, and a direct
check found no listener on 127.0.0.1:9002. The image lacks the car credential files needed by
the firmware music proxy. External Google sign-in alone cannot advance this page.

Spotify's packaged app requests `/vehicles/spotify/device_code` at
`mothership.vn.teslamotors.com:9002`. The image maps that hostname to loopback and has no
listener on 9002. The firmware contains `hermes_proxy` and its configuration assigns port 9002
to its music proxy, but the dump lacks `/var/lib/car_creds/car.crt`, `car.key` and `device.crt`.
The proxy therefore cannot authenticate to Tesla's backend. The test image also lacks a selected
driver profile and saved media credentials. Do not fabricate tokens or copy credentials out of
another vehicle. A legitimate, provisioned backend path and the user's own sign-in are the
remaining Spotify dependencies. Other sources may additionally require region, account, DRM or
backend authorization; no playback claim is made for them.

## Audio

The 2026 firmware has no standalone `AWE_command_line_tesla`, and the old Model 3 `audiod`
arguments are not accepted. Its Chromium output already writes 16-bit stereo to ALSA's
`virtual` loopback subdevice 2. A 4.88-second capture from the other side contained nonzero
audio (RMS amplitude 0.084) while a TuneIn station reported `playing`. The Model S/X `--audio`
path now captures that subdevice and sends it to the host's PulseAudio/PipeWire/ALSA player;
`./tesla status` showed `audio` up and `pactl` showed a live sink input. The path covers Chromium
web audio, not the full car DSP mix, so it does not yet establish SpotifyServer audio output.

## Follow-up: native media input and standalone Browser

The user reported that TuneIn's QtCar tabs worked on the T480 native display while its lower
web content ignored taps. With a temporary `media-touch.py --debug` bridge attached to the
already running native session, physical taps appeared as touch starts in its log; the user
confirmed that the lower content then worked. `tools/start.sh` now runs this bridge for native
and VNC. The bridge also drains DevTools replies in a background thread, so each touch no longer
waits for a round trip. This removes one source of VNC input delay, but the user has not yet
timed a new VNC session, and software rendering can still be slow.

The standalone Browser app is different from the media `chromium-app`. Before integration,
QtCar said `com.tesla.Chromium not registered yet` and Browser did not render. The profile now
starts `dbus-session-chromium`, `chromium-input` and `chromium` with a separate home, session bus,
offscreen window and localhost DevTools port 9224. It uses the media EGL pixmap shim. Initial
Chromium flags caused a crash/hang; a smaller set with `--new-window about:blank` registered
`com.tesla.Chromium` and delivered a first frame to QtCar. The Browser address bar is outside
the DevTools page viewport, so `tools/browser-touch.py` forwards taps to the offscreen X11
window. An ad hoc test loaded `https://example.org/` and followed its link to IANA by touch;
tapping the address bar invoked QtCar's keyboard.

After syncing the patch kit and rebuilding the stopped T480 image, fresh VNC run
`logs/20260928-123633/` reported all three Browser services, `browser-touch`, `media-touch`,
QtCar and the media jobs up. QtCar logged `AppWindow browser, first frame received`; selecting
Browser rendered the toolbar and blank page. DevTools showed the external Example Domain page.
A VNC tap on its “Learn more” link changed the page URL to IANA. A swipe on a temporary
3000-pixel local color-strip page moved the view from red/green to green/blue, confirming
Browser scrolling. The test fixture lived only in `chroot/tmp/` and is not tracked. Native
Browser touch remains untested on the physical panel. `tools/logsummary.py` now recognizes the
new service binaries so `./tesla status` no longer reports false DOWN results.

In short native run `logs/20260928-124308/`, `./tesla status` reported both touch bridges and
all Browser and media jobs up. `browser-touch` opened `:0`, `media-touch` connected to local
DevTools, and QtCar received Browser's first frame. The user was away, so physical Browser taps
were not tested in that run. Stop restored eDP-1 to normal 1920x1080, left the pre-mounted
`chroot/` image mounted, and the temporary sleep/idle inhibitor was released.

These tests show public Browser pages and TuneIn need no car credential. Spotify and YouTube
Music need their local Tesla music proxy for device-code/token completion. Apple Music and Apple
Podcasts fail earlier in their own login flows. Amazon Music and Audible display QR sign-in;
their account completion and playback are untested, so the missing car credential cannot yet be
asserted as their blocker.

## Follow-up: native Browser keyboard and audio output

In the user's native run `logs/20260928-124546/`, the Browser view turned black even though
QtCar logged `AppWindow browser, first frame received`. Capturing the Chromium X11 window showed
its toolbar and page, so the failure was the QtCar texture import. On native hardware, EGL
accepted the X pixmap but produced a black texture. The EGL shim now forces its XCB copy path
for QtCar on native hardware; VNC still uses that path only when direct import fails. After a
patch-kit rebuild, the user confirmed the native Browser rendered.

The same run showed QtCar's keyboard rectangle (`0 1334 1200 586`) overlapping the Browser's
touch rectangle (`10 720 1180 1020`) in the `cid` geometry file. The touch bridge forwarded
keyboard taps to Chromium, which could blur the address field. Both touch bridges now exclude
that rectangle. The Chromium input helpers' virtual touch devices are named `game-*` on native
and VNC, so the host XInput does not adopt them. The user confirmed that the on-screen Browser
keyboard works after the rebuild.

The earlier native run had `AUDIO=0`; Chromium logged `PcmOpen: plug:chromium_app, No such device`
because `./tesla` had not bound `/dev/snd` into `chroot/`. An orphaned `arecord | pacat` pipeline
from an older run remained attached to `virtual` subdevice 2; it was stopped, and teardown now
cleans up Model S/X virtual-card captures. The new native `--audio` run
`logs/20260928-130238/` started media and Browser capture helpers. ChromiumApp uses loopback
subdevice 2; Browser and `media1` sounds use subdevice 3. Both stream to the host sound server.
The user heard TuneIn on the laptop, and a local WebAudio tone in Chromium opened subdevice 3.
A separate low-level synthetic tone on subdevice 3 reached the speaker monitor. With TuneIn
playing, three seconds of monitor audio had RMS 0.207, peak 0.699 and no clipped samples;
logs showed no ALSA open failure or underrun. The user judged the sound acceptable but
imperfect, and the cause of that quality limitation is not yet established. Test audio was
measured as levels only and not saved.

The audio test ended with `./tesla stop`. A separate SSH reconnect confirmed that eDP-1 was
normal 1920×1080, both host captures had exited, and the temporary sleep/idle inhibitor was
absent. The image stayed mounted at its original `chroot/` mount point.

## Follow-up: Theater tiles on the T480

The user's `logs/20260928-131414/` had Theater YouTube and Netflix selections stuck at
“Loading...”. This was separate from YouTube Music. QtCar wrote a homepage policy but could not
create `/run/chromium/policies/chromium-fullscreen`, and its escalator could not execute
`start-tesla-chromium-fullscreen`. No Theater Chromium job or X11 window existed. The packaged
firmware runit script starts a separate `chromium-fullscreen` user, session D-Bus service and
input helper; neither the existing music web app nor standalone Browser provides that window.

The kit now creates the missing policy and TIDK runtime directories and starts
`dbus-session-chromium-fullscreen`, `chromium-fullscreen-input` and `chromium-fullscreen` as
base jobs. The latter opens a persistent offscreen `Theater` window on `about:blank`, with
localhost DevTools on 9225, before QtCar starts. This order matters: when Chromium was first
started on demand after a Theater selection, the public YouTube page loaded, but QtCar had
already scanned X11 windows and kept showing its splash. With the persistent window, QtCar
logged `AppWindow TheaterView, first frame received` at startup. `theater-control.py` watches
QtCar's exact start/stop requests, reads the selected URL from the firmware policy, navigates
the persistent page by DevTools, and returns it to `about:blank` on dismissal. A second
`browser-touch.py` instance forwards Theater taps to the offscreen X11 window. The normal
Chromium toolbar is hidden with the firmware's fullscreen flags. QtCar still logs the failed
escalator command; it no longer prevents the page from opening.

In native T480 run `logs/20260928-134338/`, the user-facing YouTube page opened, and a touch
dismissed its consent. Netflix opened its public German landing page with Sign In and catalog
previews. Twitch opened the public live catalog; touching a stream showed moving video and an
ad. Hulu's `https://hulu.com/app` redirected to the Disney+ public landing page in this test
region. TikTok rendered its feed and video content. After the fullscreen flag rebuild,
`logs/20260928-135748/` showed YouTube without a Chromium address bar. The Tutorials tile
opened Tesla's YouTube Model S playlist; touching a public video displayed playback with
subtitles. Theater content was tested on `:0` native display with `--audio`; audible Theater
output itself was not confirmed. Netflix/Disney+ sign-in, paid playback and DRM were not
attempted. These are remaining account-dependent tests, not evidence of a shared browser
failure. YouTube Music's separate music-proxy token poll remains blocked as described above.

The T480's SSH connection, AC power and sleep/lid settings were checked before testing. A
temporary `systemd-inhibit --what=sleep:idle:handle-lid-switch` process was verified after an
independent SSH reconnect during the run. After `./tesla stop`, the inhibitor was released and

pre-mounted `chroot/` image was left mounted. No power setting was changed.
