# Session 12 (2026-09-28): Model S/X laptop hardware

Firmware 2026.8.3, `model-s` branch. All hardware runs used the authorized ThinkPad T480,
`VIEWER=none` and an isolated VNC display; no Wi-Fi tests were run on the main computer.
The checkout had substantial uncommitted media work, which was preserved. The T480's image
was already mounted at `chroot/`; test stops left that mount intact.

Before unattended tests, SSH and the wired route were checked, along with AC power, logind
lid/idle policy and XFCE display power settings. A temporary `systemd-inhibit` process blocked
sleep, idle and lid switch for the duration and was verified after a separate SSH reconnect.
It was removed with `sudo kill 3414659` at the end; a separate SSH reconnect confirmed it
was absent from `systemd-inhibit --list`. No permanent power setting was changed.

## GPS

In the T480 run `logs/20260928-143037/`, `--gps 37.4419,-122.1430` started
`qtcar-gpsmanager` and `tesla-gps`. GpsManager logged a complete NMEA sentence and
`LOC_geoValidFix=true`; its data-value endpoint returned `true`. QtCar selected raw GPS.
The T480 had no attached serial GPS receiver, so real receiver passthrough remains untested.

## Wi-Fi

The first run's ConnMan worker exited at `Failed to change AppArmor hat: Operation not
permitted`. `--noprivsep` also failed on capability dropping and was discarded. The checked
`connman-no-car-apparmor-hat` patch skips only the car hat failure; the normal broker/worker
split and `-i wlan0` remain. In `logs/20260928-142224/`, the worker stayed up, QtCarConnMan
registered powered Wi-Fi, and ConnMan found seven service paths. The wired route and SSH
survived, and stop returned the adapter to NetworkManager under its original interface name.
No network was joined, so authentication, DHCP and DNS still need an actual QtCar connection
test. `tools/logsummary.py` now recognizes the `connmand` executable for status.
The user later reported that Wi-Fi worked in the T480 UI; this follow-up did not test Wi-Fi
on the main computer or independently verify a completed association.

## Camera

The T480 needed ffmpeg, matching kernel headers and v4l2loopback DKMS, installed on that
laptop. The loopback exposed `/dev/video32`; ffmpeg converted its color webcam source
`/dev/video2` to the 1280×960 BGRX feed QtCar expects. The first reverse test showed a black
view with parking lines and repeated `read-buc-deser-state failed`: the firmware expects a
car camera deserializer, absent on a desktop. A checked six-byte patch to
`CameraDevice::deserializer_ready()` returns ready for the desktop feed. After rebuilding,
`logs/20260928-143037/` showed `VIDIOC_S_FMT`, capture start and first valid frame in 1 ms.
A T480 VNC capture in R showed the webcam's red covered view under the parking lines. The
remaining `reinit-buc` escalator error did not block frames. Gear was returned to P afterward.

## Bluetooth

QtCarBluetooth initially failed to own its D-Bus names: this firmware's service script uses
user `qtbt`, while the generic wrapper chose `tesla`. The Model S/X wrapper now sets `QCUSER`
and supplementary groups for `qtcar-bluetooth`. All expected D-Bus names then appeared.

On the T480 Intel adapter, the newer LGIT/BSA stack still produced a patchram error and
repeated resets. `BT_TRACE=1` in `logs/20260928-142750/` showed several Broadcom vendor HCI
commands receiving Unknown HCI Command from the safety bridge. Passing those opcodes to an
Intel controller is unsafe: an earlier firmware command had hung it until USB power cycling.
The bridge gained local vendor success acknowledgements, enabled for the Model S/X profile
and disableable with `BT_EMULATE_VENDOR_SUCCESS=0`. In `logs/20260928-143323/`, the patchram
error and reset loop disappeared; BSA, btd and QtCarBluetooth stayed up,
`adapterAbnormal=false`, and a D-Bus `startDiscovery` call issued a standard HCI inquiry.
Discovery was stopped. At that stage no phone was paired or audio tested. Vendor commands that
need a Broadcom response payload may still fail. Keep HCI traces out of tracked files, because
they can contain device addresses.

The final T480 status was "Not running", BlueZ was active, the wireless adapter had returned
to NetworkManager under its original name, the wired link remained connected, and the
preexisting `chroot/` mount was left intact. The temporary inhibitor was released and verified
gone after another SSH reconnect.

## Bluetooth follow-up on the rooted ADB phone

The user reported that the car did not appear on the phone in T480 native run
`logs/20260928-153321/`. In that run BSA exited and its service loop restarted it, but btd
kept the dead BSA connection and `cm_inquiry_start` returned status 5 for every scan. The
phone also had an older saved Tesla bond for the same adapter, so it did not appear as a new
available device. A targeted Android Bluetooth state query confirmed that bond without a
phone screen capture. Restarting btd after BSA was running restored inquiry: the car found
the rooted phone, paired it, then connected HFP and A2DP. Android's Bluetooth state confirmed
both profiles. QtCarBluetooth received a `playing` state and media metadata. BSA later exited
again and the phone disconnected.

An all-thread signal trace showed BSA sending `SIGTERM` to one of its own threads; the host
launcher was not killing it. The reason inside the stripped firmware binary is still unknown.
The Model S/X launcher now starts `bt-watch` as soon as BSA starts. It observes BSA PID changes
and restarts btd once the replacement server is present. In `logs/20260928-155743/`, a forced
BSA termination was detected, btd restarted automatically, and the phone recovered both HFP
and A2DP. The helper also handled a later spontaneous BSA restart.

The old `a2dpbridge` route sends A2DP into AudioWeaver's `tplug`, but this Model S/X image has
no standalone AudioWeaver. The launcher now captures the firmware's 32-bit stereo A2DP
loopback on `virtual` subdevice 0 and converts it to 16-bit host playback, alongside the web
media and Browser streams. `logs/20260928-160213/` showed `audio-bluetooth` running and the
phone connected over HFP and A2DP. While the phone's Spotify session played, the T480 speaker
monitor measured RMS 0.112, peak 0.539; after pausing it, RMS fell to 0.000015. No audio was
saved. This verifies the signal reached the speakers; subjective sound quality and calls were
not tested. The phone session was returned to paused afterward.

The user has not yet personally tested the simulated GPS or camera, although the local T480
logs and reverse-view capture above verify their infrastructure. The follow-up used a
temporary T480 sleep inhibitor, verified after reconnect. After the audio test, the run was
stopped; `./tesla status` reported `Not running`, BlueZ was active, `wlp3s0` was back under
NetworkManager as disconnected, the wired local address was still present, and `eDP-1` was
restored to normal 1920x1080. The preexisting `chroot/` mount remained at `/dev/loop1`.
Raw temporary HCI captures and signal traces were deleted. The sleep inhibitor was released
and verified absent after a separate SSH reconnect. The T480 had only its direct local
Ethernet subnet route after the run; there was no default route, and we did not alter that
network configuration.
