# Session 20 (2026-11-06): the older Model S/X firmware, 2025.20.6

Goal: run `firmware/2025.20.6-models/2025.20.6.mcu2` like 2026.8.3. The user built the image and ran it
in the real chroot (run 20261106-213840); the three problems from that run are below.

## What came with it
Besides the squashfs: BIOS flash images of the car's board (`MCU2 BIOS.bin`, kernel 4.14.334;
`ICE DEV BIOS.bin`, 4.1.27) and ARM/Tegra MCU1 files (`modkernel.2020.36.16.img`,
`tegra-generic-nordump.bin`, may hold private data). None of it is used.

## Compared with 2026.8.3
Same programs, fewer services (no chromium-card, screenshare, car-assist; it has DashcamViewer).
| | 2025.20.6 | 2026.8.3 |
|---|---|---|
| glibc / libstdc++ | 2.35 / GLIBCXX_3.4.29 | 2.41 |
| kernel modules | 5.4.284-PLK | 5.4.302-PLK |
| Chromium | 127.0.6533.99 | 140 |
| firmware's Mesa | 24.0.9 (no software renderer) | 25.0.7 |

## The profile (`mcu2-patchkit/profiles/2025.20.6-models/`)
`kit.py` executes the 2026 profile's `kit.py` and replaces what depends on the build (`BASE_DIR` also
goes into the kit version):
- Patches: the same code at other offsets. `CameraDevice::deserializer_ready` by its symbol; connmand:
  the `cmp r15,rbx; jne` before `cap_get_proc`, found through the `changehat` string (VA - 0x1000 = file
  offset); Chromium's SHA routines: each scalar routine at the same distance before the SHA-NI one as
  in 140 (bytes compared), so the same relative jumps; games: the same string.
- Payload: Debian 13's files need glibc 2.39. Mesa 25.0.7 + glvnd + libraries from Debian 12 and
  bookworm-backports (at most 2.34). Debian 12's libLLVM-15 (the backport's dependency) needs 2.36, so
  libLLVM-15 and its libstdc++ (one symbol, GLIBCXX_3.4.30) and gdbserver come from Ubuntu 22.04.
- Crashpad: the firmware's handler is a no-op, Chromium 127 aborts ("recvmsg: Connection reset by
  peer", then int3), like 140. The same version's handler is in Debian's chromium-common, + libc++ 16.
  `--disable-crash-reporter` doesn't help.

## Other changes
- The escalator's framing differs: 2025's libescalator sends the bare command in one `send()` (2026:
  0xff + two lengths + command + input); the reply is the same. `escalator-stub.c` takes both (first
  byte). Seen by listening on `sandbox/rootfs-s2025/tmp/escalator` from the host. `stop-tesla-chromium`
  (2025 only) answers ok.
- `tools/start.sh`: `[ "$PROFILE" = 2026.8.3-models ]` -> `is_sx` (common.sh, the profile's car).
- CAN: no message id differs, but 24 messages' signals do (e.g. BMS_packConfig), so a profile may have
  its own database: `can_db = "models-2025"` -> `vehicle/work/can-db-models-2025.json`.

## False leads worth keeping
- "No vehicle data" in the first runs (Car Off, ----mi) was the sandbox, not the firmware. The old
  `sandbox/rootfs-s` has `/tmp/dvaccess` and sandbox-only D-Bus files left from earlier sessions; a
  fresh copy has neither. Fixed: `sandbox.sh` writes `zz-sandbox-root.conf` for S/X copies, and
  `qtcar-startup` in the service list makes the rest. Use `dbus qtcar-startup qtcar-dvserver qtcar-vehicle`.
- xdotool isn't installed on this PC (Fedora 44): a "tap" through a pipe failed silently. XTest through
  ctypes (libXtst) works.
- `mcu2s-original/.../libQtCarGUI.so.1.0.0` isn't pristine: 5 bytes at 0x272b1e8 (modified 2026-09-28,
  the retired `qtcar-gui-force-internet`). The kit restores them, so images are right.

## The first real run: three problems
- **Navigation somewhere else than the car** (all firmwares; the user suspected the arrow, but the arrow
  was right). The UI has three positions: the arrow is raw GPS `LOC_geoLocation` (= `--gps`); GpsManager's
  estimate `LOC_estimatedLocation` starts at a default compiled into the binaries (37.394287,-122.150604,
  Deer Creek Rd, Palo Alto) and only follows GPS with vehicle speed; routes start at TMServer's
  `NAV_vehicleLocation` (read in `NavRouteManager::destinationLocationSelected`), restored from
  `INAV_vehicleLocation` in TMServerSettings.db, or the default. It only updates after 3 GPS points
  and 30 m (`tm_server/min_num_gps_locations`, `min_localizer_path_length`; "Map matching not started yet").
  Fix, two parts: `RawGpsKeeper` sets `VAPI_vehicleSpeed=0.5` in GpsManager alone while parked and more than
  25 m off (one update moves the estimate; qtcar-vehicle never showed it); `./tesla start` writes
  `INAV_vehicleLocation` before TMServer starts. The route start was read as this data value, not
  from an actual route. A GPX track or serial receiver doesn't seed it: it updates once the car has moved.
  A jump of the position while parked isn't followed by the route start either.
- **TuneIn silent**: `Unknown PCM chromium_app`. 2025's asound.conf calls it `apple_music` and has no
  `chromium_voice`; the profile's kit.py replaces the flags. The PCM itself wasn't opened in the sandbox (no snd-aloop).
- **Browser touch**: `xwininfo` was missing on the host (FileNotFoundError at the first touch; Fedora
  packages it apart from xdpyinfo; the user's PC has it since 21:51). Same on any firmware. `./tesla check`
  warns, browser-touch says so at startup, setup docs list it.

False leads: setting `LOC_estimatedLocation` over HTTP makes it `<invalid>` (text can't become its list; assert
at utils/Location.cpp:64). The `tm_server/...` keys in settings.conf had no effect in the sandbox.
`LocationManagerDataStorage` (session 14's guess for the route start) isn't what the route reads.

Refused by the stub, new on 2025 and harmless so far: `start-tesla-chromium`, `thaw-`/`freeze-tesla-chromium`,
`start-gamepad-virt`, `start-`/`stop-app-performance-mode`, `stop-fleet-streaming`, `send-diag-alert`.
