# Troubleshooting

## First steps

1. **`./tesla check`**: host tools, kernel modules, the image and its kit version, maps, ports,
   settings. Every problem comes with a hint.
2. **`./tesla status`** while it runs: which service is DOWN or restarts often, and its log.
3. **`./tesla logs`** after a run (also printed when it stops): QtCar and service restarts with
   their times, segfaults from the kernel log, audio pump errors and clipping, the GPS fix,
   services that never printed anything, known error messages.

## Problem reports

Send the output of `./tesla logs` and the run's folder `logs/<date-time>/` (the summary names
it). `config` in there shows the settings used. For a service that hangs or behaves oddly,
`./tesla start --strace "SERVICE"` records what it does (`strace-SERVICE.txt` in the folder).

## Symptoms

| Symptom | Cause / fix |
|---|---|
| `port 4160 is in use` (or 4220, 4030, ...) | a leftover of an earlier run (`./tesla stop`), or the sandbox (`podman ps`, `podman kill <id>`) |
| `the image is mounted at X, not at chroot/` | it's mounted elsewhere (by hand, or an old mount point); mounting it twice would corrupt it. `sudo umount X` |
| `couldn't unmount chroot/, it's busy` | the list below it shows who holds it (a shell inside it, a file indexer, ...); stop that, then `sudo umount chroot` |
| `the image was patched by another kit version` | `./tesla build-image` (after a `git pull`) |
| Media -> USB stays at "Loading..." | the audio services didn't come up (`./tesla status`); with a kit before 2026-09-24 they waited 50 s for the car's gateway: `./tesla build-image` |
| No sound | the `pw-play` stream on another output than you listen to (`wpctl status`, Streams; `./tesla start` sends it to the default output at the start, a later change of the default doesn't move it: pavucontrol); `./tesla logs` (pump errors? audio services without output?); `snd-aloop` loaded without `id=model3`: `sudo modprobe -r snd-aloop` and start again |
| Sound stutters / mostly silent | `./tesla logs` shows many pump errors: the loopback card is taken by PulseAudio/PipeWire (install `tools/99-tesla-sound.rules`, then reload snd-aloop), or the kernel tick is coarse and the high-resolution clock didn't come up (`audio-clock.log`) |
| Bluetooth music silent | select the Bluetooth source ("Phone") in the Media app; `a2dpbridge` must run (`./tesla status`) |
| The PC's Bluetooth doesn't work after a run | `./tesla stop` normally gives it back; else `sudo modprobe -r btusb && sudo modprobe btusb`, or a reboot |
| Camera picture black | the source must deliver frames; `camera.log` has ffmpeg's messages; shift into R |
| GPS: the car doesn't move | a receiver indoors has no fix (`gps.log`: RMC status V); GpsManager not running (`./tesla status`) |
| Navigation: "maps missing" or no route | maps not installed (`./tesla check`); the destination is outside the installed region; online routing doesn't work |
| Model S/X online map stays blank; `qtcar.log` has `Bad Tile Request` | Check whether `map/MapCountry` is empty in `QtCarSettings.db`: Google rejects tile requests with an empty `region_code` (HTTP 400). See the Model S/X country setup in [features.md](features.md#offline-navigation). |
| Model S/X media panel is blank | Check `./tesla status` for `media-webapp-server`, `dbus-session-chromium-app`, `chromium-adapter`, `chromium-app-input`, and `chromium-app`; see their logs. Run `./tesla --config tesla-s.conf build-image` if the kit is old. Chromium's DevTools is local to port 9223, the web server to port 9000. |
| Model S/X native media stays at “Loading...” | Check `chromium-app.log` and `chromium-app-input.log`: both must open the native QtCar display (usually `:0`), not the cluster display (`:1.0`). Rebuild with the current kit and restart. The input helper also needs QtCar's Xauthority; `Authorization required` in its log indicates that it could not open the native display. |
| Model S/X web media shows an internet or Premium Connectivity gate | Check `logs/latest/host-connectivity.log` and `chromium-adapter.log`. Without `--wifi`, the host bridge must publish `LINK_linkState=wifi`, `LINK_wifiState=online`, `CONN_connectedToInternet=true`, and `CONN_wifiConnected=true`. With `--wifi`, the car's ConnMan owns those values. |
| Model S/X media is visible but VNC taps do nothing | Check `logs/latest/media-touch.log` for a local Chromium DevTools connection, `chromium-app-input.log` for the virtual touch device, and `touch.err`. The input config must use the virtual 1200×1920 coordinates without `range=4096`. |
| Model S/X TuneIn upper tabs work on native, but its lower content ignores taps | Update the kit and launcher so `media-touch` runs in native mode too; check `logs/latest/media-touch.log`. The T480 panel's lower content responded after this bridge was started. |
| Model S/X Browser is blank or cannot be tapped | Check `./tesla status` for `dbus-session-chromium`, `chromium-input`, `chromium` and `browser-touch`. Inspect their corresponding logs and `logs/latest/qtcar.log` for `AppWindow browser, first frame received`. The Browser uses DevTools on localhost port 9224; the media app uses 9223. |
| Model S/X Theater YouTube, Netflix or another tile stays at “Loading...” | This is the separate fullscreen Chromium stack. Rebuild the image with `./tesla --config tesla-s.conf build-image`, then check `./tesla status` for `dbus-session-chromium-fullscreen`, `chromium-fullscreen-input`, `chromium-fullscreen`, `theater-touch` and `theater-control`. Check their logs and `qtcar.log` for `AppWindow TheaterView, first frame received`; DevTools is local on port 9225. QtCar's escalator launch error can remain even when the host Theater controller navigates successfully. |
| Model S/X native Browser is black despite `first frame received` | Rebuild with the current kit. On the T480 GPU, EGL accepted the Chromium pixmap but sampled it as black; QtCar now uses the shim's X pixmap copy path for native hardware. |
| Browser address bar opens the on-screen keyboard but keys do not work | Update both the host touch bridge and image. The bridge excludes QtCar's keyboard rectangle, and the Chromium virtual touch device is hidden from native XInput; the T480 user confirmed keyboard input after these changes. |
| Clicking Model S/X media moves the host cursor outside VNC | The host adopted the Chromium virtual touchscreen. Rebuild with the current kit and ensure `tesla-touch/99-tesla-touch.rules` is installed; VNC runs name this device `game-chromium-touch`, which the rule hides from the host desktop. |
| Model S/X Spotify login says “Connection failed” | The browser reaches the sign-in page, but its device-code request goes to the firmware's mothership music proxy on port 9002. The tested image has no provisioned car certificate/key, no selected driver profile and no saved credentials; a real Tesla backend path and the user's Spotify account are needed. `SPOTIFY_sdkHasConnectivity=true` alone does not sign it in. |
| Model S/X YouTube Music stays on its login page after Google activation | `chromium-app.log` reports a failed fetch for `/vehicles/youtube_music/auth_token` on the local Tesla music proxy at port 9002. The test image has no running proxy or provisioned car credentials. Repeating activation cannot complete the in-car session until that backend path exists. |
| Model S/X TuneIn, USB music or Browser silent | Start with `--audio`; `./tesla status` must show `audiod` and `qtcar-audiod` up and the `audio` helper running. AudioWeaver (inside the S/X `audiod`) mixes Chromium (`virtual` subdevice 2), Browser (3) and the media player into amp M on the `model3` card; `audiod.log` lists the devices it opened. `snd-aloop` must have both cards (`./tesla check`); loaded with only `virtual` from an older start: `sudo modprobe -r snd-aloop`. Media stays muted until a source plays in the Media app. `chromium-app.log` with "Cannot get card index for virtual": the firmware's users can't open the cards (host audio group with another gid than the chroot's 29, e.g. Fedora's 63); `./tesla start` grants the chroot's gid an ACL on the loopback cards (`SND_ACL=` in the run's `state`). `audiod.log` "Cannot start alsaloop-chromium": an image before the kit's media bridges, `./tesla build-image`. |
| Model S/X `qtcar-vehicle` exits with 139; `qtcar-startup.log` says `shared memory ... already exists` | Stale SysV `DVSM_*` objects from an earlier run have the wrong size. Stop QtCar and start again with the updated `tools/start.sh`, which clears unattached objects belonging to the chroot's users or `dvshm` group. |
| Model S/X Wi-Fi remains at “Searching”; `connman.log` says `Failed to change AppArmor hat` | Rebuild with the current patch kit. The desktop chroot has no car AppArmor hat; the checked ConnMan patch keeps its worker running. `qtcar-connman.log` should then report `/net/connman/technology/wifi` with `Powered true`. A scan does not prove association; use QtCar settings to join a network. |
| Model S/X Bluetooth cannot find the phone after `bsa_server` restarts | Use the current launcher: its `bt-watch` helper detects a new BSA process and restarts `btd`, whose old socket otherwise returns `cm_inquiry_start error 5`. Check `bt-watch.log`, `bsa_server.log` and `btd.log`; a forced BSA restart recovered the rooted phone's HFP and A2DP connections on the T480. Rebuild with the current kit if QtCarBluetooth cannot own `com.tesla.Bluetooth` (it must run as `qtbt`). The Intel adapter also needs locally acknowledged Broadcom vendor commands; `BT_TRACE=1` records HCI traffic, and `BT_EMULATE_VENDOR_SUCCESS=0` disables acknowledgement for diagnosis. Do not forward Broadcom vendor commands to Intel hardware. |
| Model S/X phone pairs but Bluetooth music is silent | Start with `--audio`: AudioWeaver in `audiod` reads A2DP from the `virtual` card (subdevice 0); check `audiod.log`, that the phone shows A2DP connected and that its media is playing, and select the phone as source in the Media app. |
| Model S/X reverse camera stays black and `qtcar.log` repeats `read-buc-deser-state failed` | Rebuild with the current camera patch; the desktop V4L2 source has no car deserializer. Check `camera.log` for ffmpeg errors and that the source delivers frames. The T480 webcam's covered view appeared red in the successful test. |
| Model S/X GPS does not show a fix | With a fixed `--gps LAT,LON`, check `qtcar-gpsmanager.log` for NMEA and `LOC_geoValidFix=true`. For a physical receiver check `gps.log` and its `/dev/tty*` access; physical passthrough was not tested on the T480. |
| Model S/X: a video, game or other app doesn't start; `qtcar.log` says the escalator failed | `escalator-stub.log` in the run folder lists every request: `refused: <command>` = not in the stub's table (`mcu2-patchkit/profiles/2026.8.3-models/src/escalator-stub.c`). The car's escalator is never run here |
| Model S/X: chromium, chromium-app or chromium-fullscreen "crashed (segmentation fault)" at every stop | an older `./tesla`: the teardown now stops the Chromium browsers first (they crashed when their session D-Bus went at the same time) |
| Model S/X `--native` without a GPU Mesa drives: black screen, `qtcar.log` full of `MESA: error: Failed to attach to x11 shm` | Software rendering hands frames to the X server as MIT-SHM segments of QtCar's user; an X server of another user can't attach them. The stick runs Xorg as root (that fixes it there); on your own desktop use the GPU, or VNC (its Xvfb runs as root) |
| A setting or car value doesn't stick | QtCar stores it in its settings DB in the image; `vehicle/qtcar-settings.py` edits it |
| The host desktop reacts to touches | the udev rule for tesla-touch isn't installed (`./tesla check`) |
| Arcade: Beach Buggy Racing 2 ignores taps | it renders in software and runs at a few frames a second (`/run/qtcar-sv/cobalt.log` in the image: "DRI2: could not open /dev/dri/card0"); hold a tap longer, or use `--native` with an Intel GPU |
| Arcade: the car doesn't steer, "no device path found for game-steering" | start with `--vehicle` (qtcar-vehicle makes the device); the image needs the current kit (`./tesla build-image`) |
| Arcade: a game window with a title bar, in the wrong place, or MAME ignores COIN/START | the window helper isn't running (`game-windows.log` in the run folder) |
| QtCar restarts right after the start | normal once: it applies the car configuration and restarts itself (`events.log` gives the reason) |
| The stick: black screen for minutes, `./tesla status` shows everything running | the stick is too slow (cheap USB 2 sticks stall on small synchronous writes); `IMAGE_RAM` (default on a stick) keeps the writes in RAM. Check the stick with `f3probe` (fake capacity corrupts the image) |
| The stick shows a console instead of QtCar | the reason is above the help text; `./tesla start` failed 3 times in a row: `cd ~/mcu2-desktop; ./tesla logs`, `logs/session.log`; `tesla-start` tries again. Boot option "software rendering" if the GPU is the problem |
| The stick: no camera with `--secure-boot` | the kernel refuses the unsigned v4l2loopback module under Secure Boot; build without it and turn Secure Boot off |
| A service's own messages | `syslog.log` in the run folder (what the services send to syslog) |
| Many ERROR lines in `qtcar.log` | normal: services, hardware and online servers that aren't there |
